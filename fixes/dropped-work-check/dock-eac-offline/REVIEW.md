## VERDICT: CHANGES NEEDED (do not queue as -1)
Two blockers, both small:
1. The host CI check `tests/host/check-dock-start-program.py` will fail to compile with this patch (MadeiraConfig is not in that compile).
2. The path "eldenring.exe" is very likely wrong: it is resolved against the install folder, and Elden Ring's exes are believed to sit in a `Game/` subfolder (see 2a). Unverified, but if so the patch does nothing.

Everything else is fine or low risk.

## (1) Compile, by reading
- `static let eacOffline` and `private static func recommendation(_:)` inside `enum DockStartProgram`: legal. A private static func is callable from `static func chosen` / `setChosen` in the same type. No `self` or instance use.
- **BLOCKER: `MadeiraConfig.flag(...)` is not visible to the host test.** App target: fine (DockStartProgram.swift, MadeiraConfig.swift and the call sites are all in the app target; pbxproj lists DockStartProgram.swift). But `tests/host/check-dock-start-program.py` line ~169-172 compiles exactly two files:
  `subprocess.run([compiler, '-swift-version', '5', str(app / 'DockStartProgram.swift'), str(temporary / 'main.swift'), '-o', str(binary)], check=True)`
  `DockStartProgram.swift` today imports only Foundation and uses no app type. With the patch it references `MadeiraConfig`, so swiftc fails with "cannot find 'MadeiraConfig' in scope" and macOS CI (`--require-swift`) goes red. Locally it just SKIPs, which hides it. Fix options (author's choice): (a) keep the file Foundation-only and read the flag at the call sites / pass it in, e.g. `static var eacOfflineEnabled: () -> Bool = { true }` assigned at app start from `MadeiraConfig.flag("MADEIRA_DOCK_START_EAC_OFFLINE")`; (b) add a stub to the test's main.swift (`enum MadeiraConfig { static func flag(_: String, fallback: Bool = true) -> Bool { true } }`), which works but is a test-only workaround. The 5 call sites of `chosen` (ContentView 4010, GetHelpView 314/315/377, ClaudeHelp 252, SteamGames 2064) all use the default argument, so (a) with a hook is the least invasive.
- `MadeiraConfig.flag(_ name: String, fallback: Bool = true)` signature matches the call; default `true` = on unless `env.NAME = 0` in madeira.cfg or env var 0. Matches README. It takes a lock-protected cache (MadeiraConfig lines 44-85), cheap, thread-safe; `chosen` is called from `.onAppear`, body-time code and the Dock start; fine.
- The existing check line `static let recommended: [Int: String] = [252490: "RustClient.exe", 244210: "acs.exe"]` (check-dock-start-program.py line 64) is untouched by the patch, so that grep still passes. The same script's Swift fixture (lines 119-126) tests recommended games via `chosen`/`setChosen` with a private UserDefaults; it will still pass once the compile issue is solved, provided the hook default is `true` or the test stubs it (1245620 is not in the fixture).
- Catalog: the switch is not in `ConfigCatalog.generated.swift` (the UNITY_DATA switch is, line 44). Generated file; the build thread's regeneration/other check-*-switch tests may require an entry. Unchecked.
- Doc comment line is long, one line says "believed ... (unchecked)": cosmetic.

## (2) Behaviour for a user who never chose for 1245620
`chosen()` now returns `"eldenring.exe"` (flag on). At a Dock start (ContentView 4010-4013) `apply(launcher: steamEntry.program, program: "eldenring.exe", folder: installFolder, ...)` runs.

a. **Path is install-folder-relative.** In apply(): `let source = folder.appendingPathComponent(program)` then `guard files.fileExists(atPath: source.path) else { return .failed("\(program) is not in the game's folder") }`. `folder` is `.../common/<installDir>`. The picker also lists folder-relative paths (the existing test uses "Binaries/Win32/Borderlands2.exe"). Elden Ring's install is (from memory, not verified here) `ELDEN RING/Game/eldenring.exe` and `ELDEN RING/Game/start_protected_game.exe`, with Steam's launch entry `Game/start_protected_game.exe`. If so the recommended value must be `"Game/eldenring.exe"`; with the patch's `"eldenring.exe"` apply() returns .failed on every start, logs `[dock-start-program] ... failed: eldenring.exe is not in the game's folder` as an error, and changes nothing (safe, but the fix is inert). The README's "Unchecked" item covers "sits beside it" but the code needs the folder-relative path either way. Needs a real file listing (player log `[start-scan] ... entry:` line, or Steam depot) to confirm. Unchecked.
b. **Exe missing:** safe. The `.failed` return comes before any file is touched (source check precedes move/copy). Steam's launcher stays; Elden Ring starts through EAC as in 0.2.101 (and fails on EAC as before).
c. **Launcher already is eldenring.exe** (case-insensitive): `swapping` is false, so the restore branch runs: `removeDataLink` (only a symlink named `eldenring_Data`, none exists), no kept file, returns `.unchanged`. No harm. Log line still printed because `program != nil`.
d. **Game not installed / entry unknown:** `steamEntry` comes from SteamDirectStart.choose, which requires the launch exe to exist on disk (`onDisk(path ...)`, SteamGames ~292). Not installed or entry not an .exe on disk: `steamEntry` is nil, apply() is not called, and ContentView logs `program=eldenring.exe not used: Steam's launch entry is not known` as an error (line ~4020 `else if program != nil`). Noise only. Note this error line will now appear for every Elden Ring Dock start without an entry; acceptable.
e. **Swap itself (right path assumed):** start_protected_game.exe moved to `start_protected_game.exe.madeira-launcher`, a copy of eldenring.exe takes its name. Not Unity (`eldenring_Data` does not exist), so `.swapped`. Repeats are cheap: `contentsEqual` then `.unchanged` (reads ~2 exes each start, as for Rust). Unchecked: whether Elden Ring runs when its exe is renamed (it is only a file name from the game's view; modders start it directly, but I did not verify any renamed-copy case), and whether it reaches a menu offline under Wine/FEX here.

With the flag off at pick time the key is removed (and `chosen` is nil because `recommendation` is nil), also fine.
g. **Other recommended games unchanged:** `recommendation` checks `recommended[appID]` first, so Rust 252490 and Assetto Corsa 244210 behave exactly as in 0.2.101 regardless of the switch (the off-switch does not touch them; README does not claim it does). Non-recommended games: `recommendation` is nil, so `setChosen(nil)` removes the key as before, `chosen` returns nil as before.
h. Other users of `chosen`: Game details row (SteamGames 2064) now shows "eldenring.exe" for a never-chosen user (not "Steam's choice"); the `dockProgram != nil` footer text "Madeira puts a copy ..." shows. ## (3) Does "off" restore 0.2.101 behaviour?
Mostly yes. With `env.MADEIRA_DOCK_START_EAC_OFFLINE = 0`, `chosen(1245620)` is nil for a user with no stored value, so the next Dock start calls `apply(program: nil)`: restore branch, `kept` exists, `removeItem(target)` (the copy) then `moveItem(kept, target)`; returns `.restored`. So a game that is already swapped gets its launcher put back at the next Dock start (needs `steamEntry != nil`, i.e. the launcher name resolved; since the swapped file has the launcher's name and is an .exe on disk, it resolves). Same for a user whose stored value is "" (also nil).
Not restored by the switch: (i) a user who explicitly picked or Get-Help-undid to "eldenring.exe" (stored string; switch off leaves it, exactly like 0.2.101 would with a manual pick); (ii) the restore only happens at a Dock start, not at the moment the line is edited. Both acceptable but README should say "takes effect at the next Dock start" and that an explicit pick stays.
Restore in this code path is the same code as for Fallout NV; the host test covers `apply(program: nil)` after a swap ("steam"/"after").

## (4) Steam verify/update/cloud risk from the swap (existing mechanism, new game)
- Verify files: Steam sees start_protected_game.exe differ from the manifest and re-downloads it, overwriting the copy. The kept file is left stale. Next Dock start: target exists and kept exists, `contentsEqual(target, source)` false, so `removeItem(target)` then copy again; the swap re-applies. OK (the existing test "repaired" covers it).
- Update that changes start_protected_game.exe: kept holds the old one; restoring later puts the old launcher back, and Steam then repairs it on its next verify/update. Update that changes eldenring.exe: the copy no longer equals source, so it is refreshed at the next start. Low risk.
- Stray `*.madeira-launcher` file in `Game/`: Steam ignores unknown files on verify (not deleted); uninstall removes the folder. Disk cost: one extra exe copy plus kept launcher (sizes unchecked, tens of MB).
- Cloud saves: Steam Auto-Cloud is keyed by app ID and runs in the client around launch/exit, not by exe name, so the swap does not change it. Unchecked: whether an offline/no-EAC start of Elden Ring changes which save file it reads (modded/offline starts of this game are known to use a different save extension in some setups; I have not verified for the plain direct start). If the game uses a different file, the player's online save is not touched, but progress would live separately. Also, FromSoftware's terms concern online play; this patch is offline only.
- No EAC files are touched (`EasyAntiCheat/` untouched). The patch only swaps the file Steam launches.
