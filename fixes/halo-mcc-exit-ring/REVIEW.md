# REVIEW: halo-mcc-exit-ring-1 (second pass, fresh reviewer, Nov 25 2026)

Verdict: OK to queue patch 1. Patch 2 is safe but may do nothing for Halo; one change recommended (section 7). Both patches apply cleanly with `patch -p1 --dry-run` to the 0.2.101 sources (checked). Nothing was compiled or run (unchecked).

## 1. What could break
- Speed and memory, MCC only. The ring is global: `IosBlockRingEntriesRT = IosBlockRingEntriesMax` (65536) applies to EVERY thread of the process (Module.cpp: `if (IosBlockRingForce && !(XpOpt ...)) IosBlockRingEntriesRT = IosBlockRingEntriesMax;`). Core.cpp CreateThread allocates `(N + 2) * 8` bytes and memsets it per thread: 512 KB + 16 B per thread. Halo MCC is Unreal with dozens of threads: 50 threads = ~25 MB, 100 = ~50 MB, on a 4 GB iPad where Satisfactory already fails. Not measured (unchecked). Plus every translated block runs ~10 extra instructions (JIT.cpp ring store). A slowdown or a jetsam kill could hide the real exit(1) or change timing. Judge the MCC result with that in mind.
- The probe snapshot buffer (`IOS_XP_SNAP_N 65536`, 512 KB) is already allocated for every game when the probe is on, so patch 1 adds nothing there.
- Other crash dumps: `IosBlockRingForce` also makes the ring exist for Core.cpp ~1844 (crash block dump, "the newest 4096") and ntdll's `ios_cmd` reporters. MCC crashes/exits will now print block lists they did not before: more log volume. Harmless, not measured.
- Exe-name risk: the match is `_stricmp(HistoryName, "MCC-Win64-Shipping.exe")` where HistoryName = BaseName of the process exe. If the game is started through a launcher that execs a different process name, the ring stays off. The README log shows the exit from MCC-Win64-Shipping.exe itself, so likely fine (unchecked that this is the same process as the FEX init).

## 2. Files and paths touched, and who else uses them
- Patch 1: `FEX/Source/Windows/ARM64EC/Module.cpp`, ProcessInit, the line `FEXCore::Core::IosBlockRingForce = ... Overwatch.exe ...`. Other readers of `IosBlockRingForce`: Core.cpp CreateThread (~649) and JIT.cpp block prologue (~938). Both only read it. Every game passes through this line, but the new term is false unless the exe is MCC-Win64-Shipping.exe, so other games compute the same value as 0.2.101.
- Patch 2: `wine/dlls/ntdll/signal_arm64ec.c`, `ios_xp_exit_event` only, called from NtTerminateProcess (~5556: `ios_xp_exit_event( exit_code ? "NtTerminateProcess (exit code not 0)" : "NtTerminateProcess" )`). This runs in EVERY game when the probe is on (default: `ios_xp_mode = ... buffer[0] == '0' ? 1 : 2`, so on unless MADEIRA_EC_EXIT_PROBE=0 and CRASHMAILER_DUMP not 0). Games without a ring: before = "no block ring on thread <first>", after = "no block ring on thread <exiting>" (different tid in a log line only). Games with MADEIRA_BLOCK_RING=1 set by the user: dump may now be the exiting thread (see 3).
- Not touched: `ios_xp_blocks`, the second use of `ios_xp_main_teb` at ~4959 (noncontinuable raise, still main thread only).

## 3. Invariants (Overwatch 2 especially)
- OW2: patch 1 gives the same value for Overwatch.exe (`(A || HaloRing) && !Cm && !Ring` with HaloRing false). Ring size, "block ring on" log line and exit-probe-2 line unchanged. The ring-on log line says "for Overwatch.exe..." style text using AppConfigName, unchanged.
- OW2, patch 2: if `ios_xp_main_teb` has a ring (TEB+0x1710 nonzero), `main_ring` is nonzero and the code takes the `else` branch = `ios_xp_blocks( why, ios_xp_main_teb )`, same as 0.2.101. So with a first-thread ring it changes nothing. CHANGES in three cases: (a) first thread has no ring AND exiting thread differs: now dumps the exiting thread (the intent). (b) The first thread already exited: Module.cpp ~3807 stores NULL into its TEB+0x1710 before freeing, so `main_ring == 0` and the exit thread is dumped. For OW2 that is a real, probably better, change, but it is a change. (c) `ios_xp_main_teb` NULL: before, "no block ring on thread 0000"; now the current thread is tried. Also if the first thread's TEB memory is gone, `ios_cmd_read` returns 0 (it checks `ios_cmd_readable`), so `main_ring = 0`, no crash.
- Must stay: probe printing is once (`ios_xp_exit_done` latch), `ios_xp_enter/leave` pairing unchanged (new code sits between them), the "exit: ... main thread %04lx" line unchanged.

## 5. Compile check (by reading; not compiled)
- Patch 1: `const bool HaloRing = ...` inside the existing `{ }` block, C++, fine. `HaloOpt[1] == '\0'` is only read when `HaloOpt[0]=='0'` (short-circuit), safe. `IosBlockRingForce` is `uint32_t`; assigning a bool-valued `&&` expression was already done. `_stricmp` and `HistoryName.c_str()` already used on the same line. No problem seen.
- Patch 2 (C): `ULONG_PTR main_ring = 0;` is the first statement of the `if (!InterlockedExchange...) {` block, before `ERR`, so C89 order is fine. `ios_cmd_read( ULONG_PTR addr, void *buf, SIZE_T len )` returns SIZE_T, defined at line 4097, before 4746, so no prototype needed. `(ULONG_PTR)ios_xp_main_teb + 0x1710` and `sizeof(main_ring)` match what `ios_xp_blocks` itself does (`ios_cmd_read( (ULONG_PTR)teb + 0x1710, &ring, sizeof(ring) )`). `ios_xp_blocks( const char *, TEB * )` matches both calls. `NtCurrentTeb()` returns TEB*. No problem seen; `-Wall` unused-variable: none.

## 6. Is the off switch real
- `MADEIRA_HALO_EXIT_RING = 0`: `HaloRing` false, so `IosBlockRingForce` is false for MCC (unless `MADEIRA_BLOCK_RING` is set, which already enabled a ring in 0.2.101). `IosBlockRingEntriesRT` stays at default 4096 because it is only raised under `if (IosBlockRingForce && ...)`. Core.cpp `RingOn` is then 0, so no ring and no memory cost. FEX side = 0.2.101. Only "0" exactly (HaloOpt[1]=='\0') switches it off; "00" or "false" do not.
- Not identical to 0.2.101 in one place: patch 2 has no switch (ntdll does not read MADEIRA_HALO_EXIT_RING). With the switch off, the exit log differs only in the tid in "no block ring on thread NNNN". README says "Off = identical to 0.2.101": soften to "identical except that tid".
- `MADEIRA_BLOCK_RING = 0`, `MADEIRA_EC_CRASHMAILER_DUMP = 0` also force off (kept in the same expression). `MADEIRA_EC_EXIT_PROBE = 0` keeps the ring at 4096 entries (Module.cpp XpOpt check), which also makes ntdll's probe off.
- Ring log line "block ring on for {}" prints for MCC too, so the active state is visible in the log.

## 7. Verdict and changes
OK to queue patch 1 as is. Patch 2: OK to queue, with this concern.
- Concern (the main one): patch 2 only helps if the first thread (`ios_xp_main_teb`, set in `ios_xp_read_switch`) has NO ring. Module.cpp ~3348 puts the ring pointer in TEB+0x1710 for every thread that goes through FEX thread creation. The Halo "no block ring on thread 0000" line came from a run with the ring OFF, so it does not show whether thread 0000 gets a ring once the ring is on. If thread 0000 is a normal FEX guest thread it will have a ring, `main_ring` is nonzero, and the dump is again thread 0000, not 0024 = the whole point is missed (unchecked; needs a device run).
- Recommended change (small, still log only): keep the main-thread dump as now, and if the exiting thread differs from the main thread and has a ring, dump it as well (second call of `ios_xp_blocks( why, NtCurrentTeb() )` inside the same `ios_xp_enter/leave`; the snapshot buffer is reused, one printer at a time already). Then Halo gets the 0024 list in either case; OW2's existing output is unchanged and only gains an extra list when the exit is on another thread. Cost: more log lines (~up to 65536-entry list per dump; check the existing line limit `lines` in `ios_xp_blocks`).
- Also: soften README "Off = identical" (section 6), and add to README the per-thread memory warning (50-100 threads = 25-50 MB).
